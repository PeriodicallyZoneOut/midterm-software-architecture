Mô hình 4+1 — Góc nhìn 4 & +1 Scenarios

DEPLOYMENT VIEW (K8S) & CHỊU LỖI (+1)

  • Kubernetes Topology (release/kubernetes-manifests.yaml):
    • Gồm 12 Deployments và 12 Services. Chỉ frontend-external mở LoadBalancer :80->8080; toàn bộ dịch vụ nội bộ dùng ClusterIP.
    • Ánh xạ cổng đặc biệt: Container emailservice chạy cổng 8080 nhưng Service mở cổng 5000 -> targetPort: 8080.
  • Kiểm tra sức khỏe & Giới hạn tài nguyên (Probes & Resources):
    • Sử dụng native grpc readiness/liveness probes cho các dịch vụ gRPC, httpGet /_healthz cho frontend và tcpSocket :6379 cho redis-cart.
  • Kịch bản chịu lỗi (+1 Scenarios — Fault Isolation):
    • Non-Critical: Tắt adservice (timeout 100ms) hoặc recommendationservice → frontend chỉ log.Warn, trang web vẫn trả HTTP 200 OK.
    • Critical: Tắt redis-cart hoặc productcatalogservice → ném RpcException, trả HTTP 500 và tự phục hồi khi Pod Ready.

Phần 3 · Data Schema / Data Model

MÔ HÌNH DỮ LIỆU: REDIS, JSON & PROTOBUF

Redis Cart Schema

  • Baseline không dùng SQL DB mà dùng redis-cart:6379
  • Key là chuỗi user_id (từ cookie shop_session-id)
  • Value là mảng byte nhị phân Cart.ToByteArray()
➡

JSON Static Schema

  • products.json lưu 9 sản phẩm nạp thẳng vào RAM
  • currency_conversion.json lưu tỷ giá chuẩn ECB
  • Truy xuất tốc độ cao trong bộ nhớ, không tốn I/O ổ đĩa
➡

Exact Money Model

  • Message Money tách int64 units và int32 nanos
  • Tránh hoàn toàn sai số dấu phẩy động IEEE 754
  • OrderResult chốt giá snapshot trả về ngay lúc đặt hàng

Phần 4 · Security & Concurrency View

BẢO MẬT CONTAINER & XỬ LÝ ĐỒNG THỜI

Trust Boundaries

  • 3 vùng: Internet → frontend → gRPC ClusterIP → Redis
  • Kiểm tra đầu vào tại validator.go và charge.js
  • Đề xuất thêm Istio mTLS & NetworkPolicy cho Redis
➡

Pod SecurityContext

  • Toàn bộ 12 Deployments chạy runAsNonRoot: true (UID 1000)
  • Bật readOnlyRootFilesystem: true chống ghi tệp độc hại
  • Tắt allowPrivilegeEscalation & drop: ["ALL"]
➡

Concurrency View

  • Go Goroutines & .NET Async ghép kênh trên HTTP/2
  • AddItemAsync dùng mẫu Read-Modify-Write không khóa
  • 2 request cùng user_id đồng thời có thể gây Lost Update

Tổng kết & Đánh đổi Kiến trúc

ĐÁNH ĐỔI KIẾN TRÚC (TRADE-OFFS) & KẾT LUẬN

  • Polyglot gRPC + Protobuf vs. Chatty Calls:
    • Hợp đồng protos/demo.proto giúp 5 ngôn ngữ giao tiếp chặt chẽ trên HTTP/2, nhưng thiếu API batch khiến frontend và checkoutservice phải lặp N cuộc gọi Convert/GetProduct.
  • Synchronous Orchestrator (checkoutservice) vs. Choreography (EDA):
    • Luồng PlaceOrder() tập trung giúp dễ đọc code và trả ngay kết quả đặt hàng, nhưng phụ thuộc thời gian chạy vào 5 dịch vụ và chưa có bước hoàn tiền bù trừ (Saga Refund) nếu giao hàng lỗi.
  • Stateless Checkout & In-Memory Store vs. Persistent RDBMS:
    • Dùng products.json trong RAM và redis-cart (emptyDir) giúp triển khai Kubernetes cực nhẹ và dễ nhân bản, đổi lại đơn hàng chỉ là OrderResult tạm thời không lưu lịch sử lâu dài.
